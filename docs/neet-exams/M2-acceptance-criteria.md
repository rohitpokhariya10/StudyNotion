# M2: Acceptance Criteria (defined before any fix)

**Scope:** Milestone M2 only, per the approval of 2026-10-10.

**Approved decisions:**

1. Monitoring raises flags for human review; it never submits automatically. Deadline auto-submit stays.
2. Monitored mode is restricted to adults. Practice mode is unaffected.
3. Phone and email are no longer copied onto attempts; ownership is tracked by `userId`.
4. The product is "Prahit NEET Mocks", served at `/neet`, with compatibility redirects.
5. NTA NEET UG 2026 scoring applies:
   - 180 minutes.
   - A dropped or invalid question gives **+4 to every appeared candidate**.
   - Multiple-correct and all-options-correct questions are handled separately.

Each item has an ID, a measurable criterion and the test that proves it. A fix is accepted only when its proving test exists, fails before the fix (where practical), and passes after it.

Defect IDs refer to [01 audit](01-existing-architecture-audit.md).

## A. Server-authoritative timers and expiry

| ID                            | Criterion                                                                                                                                                                                                                                                                     | Proof                                                                       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| T-1 Sweeper                   | An `IN_PROGRESS` attempt whose `expiresAt` passed at least 30 s ago, and that nobody reads, is finalised by one sweep. Two concurrent sweeps plus a manual submit produce exactly one result with reason `TIME_EXPIRED`. Answers saved before the deadline are scored.        | Integration: `sweeper finalises abandoned expired attempts exactly once`    |
| T-2 Session covers exam (R-3) | `start` and `resume` re-issue the session cookie when the token expires before `expiresAt + 30 min`. The new token keeps the same `sessionVersion`. A token revoked by logout (`sessionVersion` bump) is still rejected with 401.                                             | Integration: `exam start extends a short session; revocation still applies` |
| T-3 Policy bump (R-3)         | When the user has not accepted the current policy version, the in-progress exam calls `PUT …/responses`, `POST …/heartbeat`, `…/session`, `…/submit` and `…/proctor-events` **do not** return 428. Registration, `ready`, `start`, listing and `result` **still** return 428. | Unit: `auth middleware policy gate exemptions`                              |
| T-4 Deadline unchanged        | All existing timer and expiry integration tests stay green: manual submit vs expiry, late writes rejected, a premature `TIME_EXPIRED` rejected.                                                                                                                               | Existing integration suite                                                  |

## B. Durable, revision-safe autosave

| ID                                           | Criterion                                                                                                                                                                                                                                                                                                          | Proof                                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| A-1 Final seconds (F-2)                      | When less than 15 s remain, each enqueued write is sent with **0 ms debounce**. At expiry the controller flushes pending writes, with a budget of at most 2 s, **before** calling `submit(TIME_EXPIRED)`. A write made 2 s before the deadline reaches `saveResponses` before `submitAttempt`.                     | Vitest: `flushes final-seconds answers before timeout submission`                          |
| A-2 Cross-tab/crash recovery (F-3)           | Pending writes are persisted under an **attempt-scoped** key. A new controller with empty `sessionStorage` (a new tab or a crash restore) recovers them and sends those with `seq` greater than the server's `seq`. Legacy per-session keys are migrated. Every NEET key for the attempt is removed on completion. | Vitest: `recovers unsent answers in a new tab`, `clears all attempt storage on completion` |
| A-3 Offline without the `online` event (F-5) | While `navigator` reports offline and no `online` event fires, the queue still retries sending with backoff (at most 15 s between attempts). When the transport succeeds, the pending count reaches 0.                                                                                                             | Vitest: `retries offline writes without an online event`                                   |
| A-4 Invalid write (F-4)                      | A write rejected with a drop code leaves the phase `active` with inputs enabled. A non-blocking error is shown, and heartbeats and the deadline continue.                                                                                                                                                          | Vitest: `an invalid write does not freeze the exam`                                        |
| A-5 `save-error` recoverable                 | From `save-error` with time remaining, `returnToExam()` restores phase `active`, edits are accepted and the queue resumes.                                                                                                                                                                                         | Vitest: `save-error can return to the exam`                                                |
| A-6 Revision safety (unchanged)              | Stale and duplicate writes never overwrite newer answers. The save acknowledgement contains exactly the written questions. The DB projection returns only those questions.                                                                                                                                         | Existing integration tests, plus an assertion on the response length                       |
| A-7 Zero acknowledged loss                   | In the performance smoke (C-3), every `(attemptId, questionId, seq)` acknowledged by the server is present in the database with an equal or higher `seq`.                                                                                                                                                          | `load/neet-smoke.mjs` verifier                                                             |

## C. Refresh and reconnection

| ID                         | Criterion                                                                                                                                                                                                                                                                                                                | Proof                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| R-a Same-tab refresh (F-1) | After a reload in the same tab (the session ID is in `sessionStorage` and no live peer tab claims it), `activate()` reuses that session ID. The server records **no takeover**: `sessionClaims` is unchanged and there is no `DUPLICATE_SESSION` event. A duplicated tab (a live peer holds the same ID) mints a new ID. | Vitest: `refresh reuses the tab session; duplicated tab gets a new one`. Integration: `resume with the same session is not a takeover` |
| R-b Reconnect              | After 401 or offline recovery, `activate()` resumes with the same session ID, so it is not counted as a takeover.                                                                                                                                                                                                        | Covered by R-a tests                                                                                                                   |

## E. Scoring and answer keys

| ID                         | Criterion                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | Proof                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| K-1 Frozen paper (R-2)     | After `start`, editing a question's text, options or answer key in `NeetQuestion` changes **neither** the content served on resume **nor** the key used for scoring.                                                                                                                                                                                                                                                                                                                                                                                                                              | Integration: `published paper and key versions are frozen for attempts`    |
| K-2 NTA rules              | In unit tests on `domain/scoring.js`: <br>• Single key: +4 / −1 / 0. <br>• **Multiple correct** (`correctOptionKeys.length > 1`): marking any listed key gives +4; any other option gives −1; unanswered gives 0. <br>• **All options correct** (`status: ALL_CORRECT`): any attempted option gives +4; unanswered gives 0. <br>• **Dropped/invalid** (`status: DROPPED`): +4 for **every candidate, attempted or not**. <br>• The maximum stays 4 × questions (720 for 180). <br>• Summary invariants: `correct + incorrect = attempted` and `attempted + unanswered + dropped = questionCount`. | Unit: `NTA NEET 2026 scoring rules`                                        |
| K-3 Correction and rescore | Publishing key version 2 (for example, one question `DROPPED`) and running a rescore updates every scored attempt on that paper. A second run changes nothing. `result.answerKeyVersion` becomes 2, the previous summary is kept in `resultHistory` (at most 5 entries), and attempts finalised later use v2.                                                                                                                                                                                                                                                                                     | Integration: `answer-key correction rescoring is versioned and idempotent` |
| K-4 Key secrecy            | No student-facing payload (attempt, list, session, save, heartbeat, events, result) contains `answerKey`, `correctOptionKeys` or `explanation`. Paper-version documents contain no key fields.                                                                                                                                                                                                                                                                                                                                                                                                    | Integration payload scans (extended)                                       |
